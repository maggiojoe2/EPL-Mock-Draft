# Refresh default player rankings from a source website — Spec

## Problem Statement

`public/defaults/players.csv` ships a hand-maintained snapshot of player rankings (currently labeled ADP) that drives the app's default player pool and simulated-team pick behavior. There's no repeatable way to refresh it — someone has to hand-edit the CSV, so it goes stale as the offseason/season progresses. Separately, the field is actually mislabeled: what the app calls ADP (Average Draft Position) doesn't match what the available free, easily-pullable source data actually is (Expert Consensus Ranking). And the mechanism used to line up a fantasy team's previous-year roster (`rosters.csv`) with the player pool is a bare case-insensitive name match, which silently breaks if a refreshed data source spells a name even slightly differently.

## Solution

Rename the mislabeled `adp` field to `rank` (Expert Consensus Ranking, half-PPR), and source it from a free, CORS-permissive, no-auth CSV (`dynastyprocess/data`'s `db_fpecr_latest.csv`, a maintained mirror of FantasyPros ECR data) via two paths that share one normalize/validate module: a live fetch on every app load (with silent fallback to the bundled CSV on any failure, and a banner that tells the user which one is actually being used), and an on-demand dev script (`npm run update-players`) that regenerates the bundled fallback CSV. Add a stable `player_id` (the source's FantasyPros ID) to both the player pool and `rosters.csv` so roster↔pool matching no longer depends solely on name strings, with a one-off migration to backfill IDs into the existing `rosters.csv`.

## User Stories

1. As a draft manager, I want the app to automatically pull current player rankings from a live source when I load the setup screen, so that I'm drafting against realistic, up-to-date values without manually re-importing a CSV.
2. As a draft manager, I want the app to fall back to its bundled default rankings if the live source is unreachable (offline, network error, source format changed), so that a bad network or an upstream outage never blocks me from starting a draft.
3. As a draft manager, I want a clear on-screen indicator of whether I'm seeing live or fallback ranking data, so that I know how fresh what I'm looking at is.
4. As a draft manager, I want my uploaded custom player-pool/roster CSVs to keep working exactly as they do today, so that this change doesn't break my existing workflow.
5. As a maintainer, I want a script I can run on demand (`npm run update-players`) to regenerate the bundled fallback rankings CSV from the live source, so that the fallback doesn't go stale over months/years even though it's not the everyday data path.
6. As a maintainer, I want the refresh script to refuse to overwrite the bundled CSV if the fetched data looks malformed (too few rows, missing columns, unrecognized position codes), so that a source-format change can't silently ship broken defaults.
7. As a maintainer, I want the refresh script to warn (not fail) when a rostered player's name no longer appears in the refreshed data, so that I can investigate without a plausible roster change (retirement, cut) blocking every refresh.
8. As a maintainer, I want the player pool and `rosters.csv` to carry a stable player ID from the source, so that roster-to-pool matching survives minor name-formatting differences between refreshes.
9. As a maintainer, I want a one-off migration that backfills `player_id` into the existing `rosters.csv` by matching current names against the current player pool once, flagging anything unmatched, so that I don't have to hand-edit IDs into ~12 teams' worth of rosters.
10. As a maintainer, I want the fetch-and-normalize logic shared between the live in-app path and the dev script, so that the mapping from the source's CSV columns to the app's schema is implemented once, not twice.
11. As a maintainer, I want `test-data/players.csv` and `test-data/rosters.csv` left untouched by both the live fetch and the refresh script, so that test fixtures stay stable regardless of live-source changes.
12. As a developer reading the domain docs, I want `CONTEXT.md`'s glossary to describe the renamed `rank`/ECR field accurately (what it is, half-PPR, sourced from a live fetch with a bundled fallback), so that the docs don't describe a mechanism (manual FantasyPros CSV import) that no longer reflects reality.

## Implementation Decisions

- **Field rename**: `Player.adp` → `Player.rank` throughout (`types.ts`, `csvParser.ts`, `aiSimulator.ts`, any UI copy referencing "ADP"). `CSV_COLUMNS.playerPool` header changes from `adp` to `rank`. Default-on-missing/invalid value behavior (currently defaults invalid `adp` to `9999`) carries over unchanged, just renamed.
- **Data source**: `https://raw.githubusercontent.com/dynastyprocess/data/master/files/db_fpecr_latest.csv` — confirmed free, no-auth, real CSV, CORS-permissive (`access-control-allow-origin: *`), maintained mirror of FantasyPros ECR data. Source columns of interest: `player`, `id` (FantasyPros player ID — becomes the app's `player_id`), `pos`, `team`, `ecr` (half-PPR). Full research trail: `.scratch/player-rankings-refresh/adp-source-research.md`. Note in code that this is a third-party mirror of FantasyPros data, not FantasyPros directly — worth revisiting if it ever lags or goes stale.
- **Shared normalize/validate module**: one new pure module (parallel to `csvParser.ts`'s existing parse functions) that takes raw source CSV text and produces `Player[]` (`id`, `name`, `position`, `nflTeam`, `rank`) plus the sanity-check results described below. Used by all three consumers below — implemented once.
  1. **Live in-app fetch**: on `SetupScreen`/`useSetupState` mount, fetch the source CSV directly from the browser (plain `fetch`, no caching/TTL — refetch every load, matching the simplicity of the existing `loadDefaultData` fetch of the bundled CSVs). On any failure (network error, non-ok response, parse/shape failure), fall back to fetching the bundled `public/defaults/players.csv` exactly as today. The setup screen's existing "Using default data" banner is updated to distinguish three states: live data loaded, fallback-to-bundled used (with the reason surfaced, e.g. fetch failed), and user-uploaded CSV in use (unchanged from today).
  2. **Dev script** (`npm run update-players`, new `scripts/update-players.ts`, run via a new `tsx` devDependency): fetches the same source server-side, runs it through the shared module, and — only if the sanity checks pass — overwrites `public/defaults/players.csv`. Manually/occasionally run by a developer; not scheduled or automated in CI.
  3. **One-off migration script**: fetches/normalizes current source data (or reads the just-refreshed `players.csv`), matches each existing `rosters.csv` row's `player_name` against it (reusing the same matching logic as the live matcher), and rewrites `public/defaults/rosters.csv` with a new `player_id` column populated. Unmatched rows are flagged in script output for manual review, not silently dropped or blocked. This is a one-time pass — IDs are stable across future refreshes once backfilled, so it does not become part of the recurring `update-players` flow.
- **Fail-safe sanity checks (dev script only, before overwriting the committed CSV)**: abort with a non-zero exit and a clear error message, leaving the existing file untouched, if any of: fetch fails, minimum row count (~300) isn't met, required columns are missing/empty, or position codes fall outside the known set (QB/RB/WR/TE/K/DST).
- **Roster-mismatch check**: comparing rostered player names/IDs against the freshly fetched data and warning (not aborting) on anything unmatched — runs as part of the dev script's sanity pass. This is a diagnostic aid, superseded in effect once `player_id` backfill (below) is complete, since ID-based matches won't spuriously break on name formatting.
- **Player identity / matching logic** (`buildTeamsFromImport` in `src/setup/setupHelpers.ts`, the sole place roster↔pool matching happens today): extended to look up by `player_id` first when present on the roster row, falling back to today's case-insensitive name match when `player_id` is absent. This preserves the user-CSV-upload feature (uploaded files won't have IDs) unchanged while making the app's own bundled/live data resilient to minor name differences.
- **Schema additions**: `player_id` column added to `CSV_COLUMNS.playerPool` output and to `CSV_COLUMNS.roster` (`rosters.csv` gains a `player_id` column alongside existing `team_name,player_name,franchise_eligible,previously_saved`). `Player.id` already exists in the type but is currently synthesized internally (`playerIdFromNamePos`); it switches to being read from the source's `id` field when present (live/bundled data), with the synthesized fallback presumably retained for user-uploaded pools that lack an `id` column — exact fallback behavior for `Player.id` synthesis to be confirmed during implementation against current `csvParser.ts` behavior.
- **`.env` note for future use**: not needed for this spec (the chosen source requires no auth), but if a future iteration switches to FantasyPros' official paid Consensus Rankings API, any API key must be read from a gitignored `.env`, server/script-side only, never shipped client-side.
- **`CONTEXT.md` glossary update**: the `ADP (Average Draft Position)` entry (currently at `CONTEXT.md:35`) and the related mention in the "Simulated team" entry (`CONTEXT.md:41`) are rewritten to describe `rank`/ECR accurately — what it is, half-PPR, and the live-fetch-with-bundled-fallback sourcing mechanism, replacing the outdated "sourced from a FantasyPros CSV export" description.

## Testing Decisions

- Good tests here assert on the pure, directly-testable logic (parsing, normalizing, matching, sanity-checking) and treat fetch/filesystem I/O as a thin, untested shell around it — consistent with how this repo already tests `csvParser.ts` and `useSetupState.ts`'s `loadDefaultData`, and consistent with `docs/adr/0002-defer-component-tests-for-setup-screen.md`'s decision not to add component/rendering test infrastructure.
- **New shared normalize/validate module**: tested like `src/setup/__tests__/csvParser.test.ts` tests `parsePlayerPoolCsv`/`parseRosterCsv` — feed it raw source-shaped CSV text inline as a template literal, assert on the returned `Player[]` and on the sanity-check results (row-count/column/position-code failures, roster-mismatch warnings), no mocking, no fixture files.
- **`buildTeamsFromImport` in `setupHelpers.ts`**: extend its existing test coverage with cases for id-present (matches by id even when name differs), id-absent (falls back to existing case-insensitive name match, unchanged behavior), and id-present-but-unmatched.
- **Dev script / migration script**: not unit-tested directly (they're thin I/O wrappers around the tested shared module and matching logic); acceptable to verify manually when built, consistent with how `loadDefaultData`'s fetch/try-catch shell isn't separately tested today.
- Prior art: `src/setup/__tests__/csvParser.test.ts`, `src/setup/__tests__/useSetupState.test.ts`.

## Out of Scope

- FantasyPros' official Consensus Rankings API (paid tier required for production use) — noted as a possible future swap if the free GitHub mirror proves unreliable, not built now.
- Any scoring format other than half-PPR.
- Scheduling/automating the refresh script (cron, CI) — it stays a manual, on-demand command.
- Changing `test-data/players.csv` / `test-data/rosters.csv` — these stay as-is, untouched by both the live fetch and the refresh script.
- Any UI for triggering a manual "refresh now" from within the running app — refresh happens automatically on every load; there's no separate trigger to build.
- Repeated/ongoing `player_id` migration tooling — the `rosters.csv` backfill is explicitly one-off, not a recurring part of `update-players`.
